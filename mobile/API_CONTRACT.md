# API Contract

Base: `/api/v1`. Auth: session cookie (web) or `Authorization: Bearer <token>` (mobile). Responses are `{ data }` on success, `{ message, code }` on error. Request bodies use the Zod schemas in `shared/src/validation/<domain>`; payload types are in `shared/src/types/<domain>`.

Roles: `SA` super_admin, `GA` gym_admin, `C` client. Keep this table in sync with `backend/src/routes/v1/*.ts`.

Gym locations notes:

- One gym (and its owner, the gym admin) can have several locations, shown to the owner as "My gyms". Memberships, plans, balance and products are shared by all of them: a member has one account and one weekly limit, and the visits count the same wherever they train.
- A location is `{ id, name, address, phone, latitude, longitude, mapUrl, isActive }`. `latitude` and `longitude` are the pin the owner set on the map (create and edit require both; they are `null` only on locations that existed before coordinates). `mapUrl` is an optional `https` Google Maps link the owner pasted (`''` when none): open it when present, otherwise build `https://www.google.com/maps/search/?api=1&query=<latitude>,<longitude>`. Every new gym (`POST /gyms`) starts with one location (`Main`); existing gyms were given one by the migration. `GET /gym-locations` returns every location to a gym admin and only active ones to a client (list them so the member can see where to go). The gym admin adds and edits locations and closes or reopens them with `PATCH /gym-locations/:id/status`; they are never deleted, and the last active one cannot be closed (`422`).
- `POST /attendance/check-in` takes an optional `locationId`. With one active location it is used automatically; with several the request needs `locationId` (`422` otherwise, and `422` for a location that is not an active one of the gym). Attendance records carry `locationId` and `locationName` (`null` for check-ins from before locations existed).

Class timetable notes:

- Every new gym (`POST /gyms`, or an approved sign-up request) starts with default classes (Abs, Aerobics, Zumba, Yoga, Pilates, Spinning, Cross Training, Stretching & Mobility) and no instructors, plus three standard workout programs (`Full Body Starter` beginner, `Push / Pull / Legs` intermediate, `Upper / Lower Power` advanced) with their days, exercises and how-to notes. The gym admin edits, hides, removes or replaces them (`PATCH`/`DELETE /workout-programs/:id`); gyms created before this keep what they have.

Country, language and currency notes:

- A gym has a `country` (`AL`, `GB`, `IT`, `DE` or `GR`; default `AL`), set by the super admin in the gym form (`gyms.gymFormSchema`) or by the sign-up request. `GET /me` returns `gymCountry` and `gymCurrency` (country and currency of the user's gym, both `null` for the platform owner). The app starts in the country's language (AL Albanian, GB English, IT Italian, DE German, GR Greek); a user can still pick another language.
- Currency is stored on the gym (`Gym.currency`: `ALL`, `EUR` or `GBP`), set by the server from the country (`AL` -> `ALL`, `GB` -> `GBP`, `IT`/`DE`/`GR` -> `EUR`; `COUNTRY_CURRENCIES` in `gyms` validation) and never sent by clients. Every amount of that gym (plans, products, balance, sales, its platform subscription and payments) is in it, whatever language the user picks. Show money with `gymCurrency`; amounts are never converted. The Gym object (`/gyms`) has `currency` and `countryLocked`: once the gym has any plan, product, membership, balance transaction, sale, subscription or subscription payment, `PATCH /gyms/:id` answers `422` if `country` changes.
- `GET /gym-subscriptions` and `GET /billings` rows (subscriptions and payments) have `currency` (the gym's). `GET /dashboard/platform` returns `revenueTotal`, `revenueThisMonth` and `overdueAmount` as arrays of `{ currency, amount }`, one entry per currency that has an amount (never added across currencies).
- API messages (`message` in an error body) are English texts; the web app translates the known ones. Send nothing localized and keep new messages as plain English sentences.

- A class is a weekly repeating slot: `{ name, description, weekdays: number[] (1 = Monday to 7 = Sunday), startTime, endTime (gym-local HH:MM), staffMemberId | null, staffMemberName | null, isActive }`. Send `staffMemberId: ''` for no instructor. `GET /classes` returns only active classes to a client; show them per weekday ordered by `startTime`.
- A class must end after it starts. An instructor cannot be on two overlapping active classes on the same weekday (`422` naming the clash); back-to-back is fine. Only active staff of the gym can be assigned, but a class keeps an instructor that was deactivated later. Staff are never deleted, only deactivated.

Membership plan notes:

- `POST /uploads` stores one image of the gym and returns `{ url }` (`/uploads/<gymId>/<file>`; prefix it with the API base URL). Send that `url` as `imageUrl` on a product or on an exercise of a workout program; an empty string removes the image. A `url` of another gym is rejected with `422`. Files that are uploaded but never saved are not cleaned up yet.
- Products have `category` (`supplement`, `snack`, `drink`, `merchandise`, `shake`, `smoothie`) and `imageUrl` (empty = show a default icon for the category; leaving `imageUrl` or `category` out of `PATCH /products/:id` keeps the current value). `shake` and `smoothie` are made to order: `stock` is always stored as 0 and ignored, clients still see them (even with no stock) but `POST /products/:id/purchase` returns `403` for a client and `422` unless a gym admin records the sale with `paymentMethod: 'cash'`. Show a "payable only by cash at the gym" warning for them.
- Each exercise of a workout program has `icon` (a default movement figure the apps draw: `squat`, `bench-press`, `deadlift`, `overhead-press`, `pull-up`, `row`, `lat-pulldown`, `curl`, `triceps`, `lunge`, `leg-press`, `push-up`, `plank`, `crunch`, `run`; older values such as `barbell` or `legs` are mapped to the closest one) and `imageUrl` (the gym's own photo, shown instead of the figure when set).

- The standard price list is the set of plans with a term (`monthly`, `three_months`, `six_months`, `yearly`) per `weeklyVisits` (3x to 6x, 0 = unlimited) and `gender`. Gym admins save it per gender with `PUT /membership-plans/price-grid` body `{ gender, cells: [{ weeklyVisits, type, price | null }] }` (`null` or 0 removes the price). Plans with `visit_based` or `personal_training` are extras (daily pass, packs).
- `GET /price-list` returns `{ notes: string[], photos: [{ id, url, createdAt }] }`. A photo `url` is a path such as `/uploads/<gymId>/<file>.jpg`; prefix it with the API base URL. Files are public read-only under `/uploads`.
- `GET /membership-plans` for a client returns only active plans of the client's own gender (`Client.gender`; none while unset). Each plan has `gender`, `weeklyVisits` (0 = unlimited), `type`, `durationDays`, `price` (the regular price, in the gym's currency) and `offer` (`{ id, name, price, startDate, endDate }` or `null`). The longer terms of the same gender and `weeklyVisits` are the term discounts; compute that saving against the monthly price in the app.
- Special offers (`/price-offers`, gym admin): a named, limited-time price for some plans, `{ name, startDate, endDate, items: [{ planId, price }] }` (dates `YYYY-MM-DD` in the gym timezone, both days included). One offer can hold one plan (for example 3x per week for a month at 3500 instead of 4500 for New Year) or a whole seasonal price list. Each item price must be lower than the plan's regular price (`422` otherwise) and a plan appears once per offer. The offer has `status` (`active`, `scheduled`, `ended`, `paused`, derived from the dates and `isActive`) and its items carry `planName`, `regularPrice` and `price`. `PATCH /price-offers/:id/status` pauses or resumes it; `DELETE` removes it (memberships already bought keep their price).
- While an offer is valid, `GET /membership-plans` returns it as the plan's `offer` (the lowest one if several apply). Show `offer.price` with the regular `price` struck through and the end date; a purchase (`POST /memberships`, `/memberships/subscribe`, renewals, card verification) is charged `offer.price`, decided by the server, and the membership `price` records what was paid.
  Card payments by a client (`C`) are verified with a one-time code and cannot be sent straight to `/balance/deposit` or `/memberships/subscribe` (those return `403`). Flow: `POST /payment-challenges` with `{ kind: 'deposit', deposit }` or `{ kind: 'membership', subscription }` (each with `paymentMethod: 'card'` and `card`) returns `{ challengeId, expiresAt, demoCode? }`; the member enters the 6-digit code and the app calls `POST /payment-challenges/:id/verify` with `{ code }`, which charges and returns `{ kind: 'deposit', transaction }` or `{ kind: 'membership', membership }`. Codes expire after 5 minutes, allow 3 attempts and work once; a new start replaces the open challenge. `demoCode` exists only outside production (no SMS provider yet).

- `POST /balance/deposit` and `POST /memberships/subscribe` with `paymentMethod: 'card'` also need `card: { brand: 'visa' | 'mastercard', last4: '1234' }`. Send only these two values: the app collects the number, expiry and CVC on the device, validates them, and never sends or stores them. A deposit `amount` only has to be greater than zero; deposit methods are `card` (clients and gym admins) and `cash` (gym admins only).
- `POST /memberships/subscribe` body is `{ planId, paymentMethod: 'balance' | 'card', card? }` (cash is not accepted from clients). Both return a paid membership: `active` when it starts today, `upcoming` when it is queued (see the next point). Errors: `422` for a plan of the other gender, missing gender, insufficient balance, or an existing pending membership.
- `POST /memberships` and `POST /memberships/:id/renew` (gym staff) take `paymentMethod: 'cash' | 'card' | 'balance'` (`422` for anything else); a `card` payment also needs `card: { brand, last4 }`. The membership is paid at once (balance needs enough credit). Members who pay in their own app use `POST /memberships/subscribe`.
- Payment settings: `GET /payment-settings` (gym admin and client) returns `{ acceptCard, acceptBalance, acceptCash }`, all `true` by default for every gym; `PUT /payment-settings` (gym admin) saves them and answers `422` if all three are off. Show a member only the ways of paying that are on: `acceptCard` (online and counter card payments), `acceptBalance` (paying from credit; when off, balance top-ups are off too) and `acceptCash` (cash at the counter, and the cash-only shakes and smoothies). The server enforces it with `422`: `POST /memberships`, `/renew` and `/subscribe`, `POST /balance/deposit`, `POST /products/:id/purchase` and `POST /payment-challenges` refuse a method the gym has turned off (`Card payments are not accepted by this gym.`, `Paying from the balance is not accepted by this gym.`, `Cash payments are not accepted by this gym.`), and any deposit answers `This gym does not use balance credit.` while credit is off.
- Memberships queue: a new paid membership (`subscribe`, `POST /memberships`, `renew`) never overlaps another one. Its `startDate` is the requested date, or the day after the client's last `active`/`upcoming` membership ends when that is later; `endDate` is `startDate` plus the plan duration. So 1 month, then another bought weeks before it ends, then 6 months later each start the day after the previous one ends. Read the real `startDate`/`endDate` from the response; the requested date is only a minimum.
- Membership `status` is one of `pending` (waiting for payment), `active` (started, not ended), `upcoming` (paid, `startDate` in the future), `expired`, `cancelled`. `upcoming` and `expired` are derived from the dates when read. Only the `active` membership allows check-in. `GET /memberships` returns every membership of the client; show the queue as the `active`, `upcoming` and `pending` ones ordered by `startDate`.
- `GET /balance` returns `{ balance, transactions, nextCursor }`: the newest transactions first, 20 per page (`?limit=` up to 50). While `nextCursor` is not `null`, request the next page with `?cursor=<nextCursor>` (add `clientId` again for gym admins). `balance` is always the full ledger sum, not the sum of the loaded page. Filters (all optional, combine with paging): `from` and `to` (`YYYY-MM-DD`, inclusive, days in the gym timezone), `minAmount` and `maxAmount` (>= 0; they match the size of a transaction, so `500` finds a 500 deposit and a -500 purchase). `422` when `from` is after `to` or `minAmount` is above `maxAmount`.
- `GET /attendance` returns the latest check-ins (at most 100, newest first); add `?limit=10` to get fewer.
- Cards, check-out and lockers: the gym turns them on in `GET/PUT /access-settings` (`{ cardsEnabled, lockersUseCard }`, both `false` by default; `lockersUseCard` needs `cardsEnabled`, `422` otherwise). Whether a gym has lockers at all is just whether it added any (`POST /lockers`); there is no separate on/off for that. A card (`/member-cards`) belongs to one member and has a `number` (stored upper case, unique per gym); issuing a card retires the member's previous active one, a blocked card is rejected (`422`) and a number is never reused. `POST /attendance/scan` takes a `code` that is a card number or the member code (the QR value) and toggles: it checks the member in, or out when they have an open visit; a second scan within 60 seconds of check-in is a double scan (`422`). The answer is `{ action: 'checked_in' | 'checked_out', record }`. `POST /attendance/check-out` ends the open visit (a member sends no body, staff send `clientId`; `422` when not checked in). A visit stays open until check-out or 12 hours. Attendance records carry `lockerNumber` (`null` when none).
- Lockers belong to a gym location **and a gender** (changing rooms are separated): `Locker.gender` (`male`/`female`), unique per `(locationId, gender, number)`, so a men's and a women's locker can share the same number. `POST /lockers` `{ locationId, gender, prefix, from, to }` adds a numbered range to one changing room; existing numbers are kept. If the gym's gender settings say prices and lockers are the same for both (see below), the same range is also added for the other gender automatically. A locker is taken while the visit that holds it is open and is free again at check-out. `GET /lockers?locationId=` lists them (both genders; filter by gender client-side) with `occupiedBy` (`{ clientId, clientName, since }` or `null`); `DELETE` refuses a locker in use (`409`). `POST /lockers/assign` `{ lockerNumber, code? }` puts the member's things in a locker for their open visit (`422` when not checked in, the locker is out of service, or the gym separates lockers by gender and the member's own gender is not set while the number exists in both rooms; `409` when taken; `404` when the number does not exist for the member's changing room): staff pass the member `code`; a member sends no `code`, and is refused (`403`) when the gym locks lockers with the card, where the card number (`code`) must be sent from the locker or the desk. `POST /lockers/release` frees it earlier. `GET /dashboard/client` returns `card` (active card number, or `null`), `checkedIn` and `locker` (`{ lockerNumber, locationName, clientName }` or `null`).
- `GET/PUT /gender-settings` (gym admin only) is `{ samePricesForGenders: boolean, sameLockersForGenders: boolean }`, both `false` by default and independent of each other. When `samePricesForGenders` is `true`: `PUT /membership-plans/price-grid` writes the same cells to both `male` and `female` plans regardless of the `gender` sent. When `sameLockersForGenders` is `true`: `POST /lockers` mirrors the range to both genders as described above. Extras (`visit_based`/`personal_training` plans) are never mirrored; each gender's extras are still managed separately.
- `GET /attendance/history` returns `{ records, nextCursor }` for long histories: newest check-ins first, 20 per page (`?limit=` up to 50). While `nextCursor` is not `null`, request the next page with `?cursor=<nextCursor>`. Clients only get their own check-ins.
- `GET /attendance/days?month=YYYY-MM` (client) returns `{ month, days }`: the days of that month on which the signed-in member checked in, as `YYYY-MM-DD` in the gym's local calendar, oldest first and once each (several check-ins on one day count as one). It feeds the read-only "History" calendar on the home page; `422` for a month that is not `YYYY-MM`. Use `@gym/shared/calendar` (`monthWeeks`, `shiftMonth`) to draw the month.
- `GET /memberships/history` returns `{ memberships, nextCursor }` the same way: latest `startDate` first, 20 per page (`?limit=` up to 50), next page with `?cursor=<nextCursor>`. Clients only get their own memberships. Filters (optional, combine with paging): `status` (`pending`, `active`, `upcoming`, `expired`, `cancelled`; `upcoming` and `expired` are matched by the dates like in the responses) and `from`/`to` (`YYYY-MM-DD`, inclusive) which match memberships whose period overlaps that range. `422` when `from` is after `to`.
- `POST /attendance/check-in` returns `422` when the membership's `weeklyVisits` limit for the current week is used up. A member can check in several times on the same local day (in and out); only the first entry of the day counts as a visit for the weekly limit, visit packs and `visitsUsed`. A repeated scan within 60 seconds returns `422`.
- `GET /dashboard/client` `activeMembership` includes `price` (amount paid, ALL), `visitsAllowed` (weekly visits x 4 weeks for each 28-day period of the membership (the 29th to 31st day add none); less only for memberships shorter than 28 days; 0 when `weeklyVisits` is 0) and `visitsUsed` (check-ins on that membership in the same period). `visitsEndDate` is the end of the last full 4 weeks of a weekly plan (e.g. day 28 of a 30-day month); show it, and the days remaining until it, instead of `endDate`. Show `visitsAllowed` boxes with `visitsAllowed - visitsUsed` filled. The payload also has `week: { start, today, checkedInDates, previousVisits }`: the Monday of the current week, today (gym-local `YYYY-MM-DD`), the days of this week with a check-in and the number of days with a check-in in the previous week (compare the two for the "vs last week" label), for the weekly calendar.
- `Client` payloads and the create/update client bodies include `gender` (`male` | `female`; `null` on legacy rows).

Auth routes (Better Auth, not under `/api/v1`): `POST /api/auth/sign-in/email`, `POST /api/auth/sign-out`, `GET /api/auth/get-session`, `POST /api/auth/change-password`. `GET /health` returns `{ "status": "ok" }`.

Sign-up request and rate limit notes:

- Client invite links: the gym admin creates a client with name, email, phone and gender only; it never sets a password (`POST /clients` ignores a `password`), so the client has no login yet (`hasLogin: false` on the client). `POST /clients/:id/invite` returns `201 { token, expiresAt }` once; the server stores only a SHA-256 hash of the token, a new call cancels the earlier unused link, and the link expires after 7 days. Build the link as `<web origin>/invite/<token>` (the web app shows it with a QR code; the mobile app should open the same URL or accept the token). It also works as a password reset for a client who already has a password.
- `POST /clients/:id/invite/send` with `{ token }` (the token the admin just received) emails the invite link to the client's address and returns `{ sentTo }`; the server only sends a live (unused, unexpired) link of that gym's client, otherwise `404`, and builds the URL itself from `WEB_ORIGIN` (default: the first `CORS_ORIGINS` entry), never from the request. Without SMTP (`SMTP_HOST`) development only logs the mail and production answers `503`.
- `GET /client-invites/:token` (no session) returns `{ clientName, email, gymName, gymCountry }`; `POST /client-invites/:token/accept` with `{ password }` sets the password once, ends the client's open sessions and returns `{ accepted: true }`. The client then signs in normally with the email and that password. An unknown, used, expired or inactive-gym token answers `404` with the same message. Both calls are rate limited (`429`).
- Members sign up on their own (web `/join` and `/join/<joinCode>`, and the same calls from the mobile app); none of these need a session and all are rate limited (`429`, 20 per 15 minutes per IP for the `POST`s):
  - Every gym has a permanent join code (it does not expire). The gym admin reads it with `GET /client-signups/join-code` (`{ joinCode }`) and shows `<web origin>/join/<joinCode>` as a link and QR code; `POST /client-signups/join-code/rotate` replaces it (the old one stops working at once). `GET /client-signups/join/:code` returns `{ gymName, gymCountry }` for the sign-up screen; an unknown code or an inactive gym answers `404`.
  - Sign-up form order (web and mobile): the member fills in everything on one form first (first name, surname, email, phone, gender, country, password and confirmation; with a gym link the country defaults to the gym's), then the app calls `POST /client-signups/lookup` with the email. `registered` -> stop and send them to sign in with that email. `new` or `gym_client` -> a 6-digit verification code was emailed to them: show a code step (with the countdown to `expiresAt`, a "Resend code" action that calls the lookup again, and "Change details" to go back), then `new` -> `POST /client-signups` with the form values plus `code`, `gym_client` -> `POST /client-signups/claim` with `{ email, code, password }` (the password already typed). After either, sign in and land on the community gym list (or the gym, with a join code). Nothing is created before the code is verified.
  - Step 1, `POST /client-signups/lookup` with `{ email }` returns `{ status, gymName, expiresAt }`. `status` is `new` (nobody has this email), `registered` (an account with a login exists: send the person to sign in; `expiresAt` is `null`) or `gym_client` (a gym already added this email as a client but they have no login; `gymName` is that gym). For `new` and `gym_client` the server emails a 6-digit code that is valid for 1 minute (`expiresAt`, ISO) and is burned after 5 wrong guesses; asking again replaces it, but a second lookup within 20 seconds of the first answers `429` ("Please wait a moment before asking for a new code."). Outside production no mail is needed: the code is always `111111`. In production the API sends the mail through SMTP (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `MAIL_FROM`) and answers `503` when none is configured. The code is never returned by the API.
  - `new`: `POST /client-signups` with `{ firstName, lastName, email, phone, gender, country, password, code, joinCode? }` (`country`: `AL`, `GB`, `IT`, `DE` or `GR`; `code`: the 6 digits) returns `201 { gymName }`. A wrong, missing, used or expired code answers `422`. With a `joinCode` the person becomes a client of that gym; without one they join the community (`gymName: null`). `gymId` is never sent. The app then signs in with `POST /api/auth/sign-in/email`.
  - `gym_client`: `POST /client-signups/claim` with `{ email, code, password }` sets the client's password once and returns `{ gymName }`; a wrong, used or expired code answers `422`. Then sign in as usual.
  - A community member is a `client` whose `/me` has `gymId: null`. They can only call `GET /community/gyms?country=` and `POST /community/join` with `{ gymId }`. `GET /community/gyms` returns `{ country, gyms }`: the active gyms of one country (`id`, `name`, `location`, `country`, `currency`, `address`, `contactEmail`, `contactPhone`, `businessHours`, `opensAt`, `closesAt`, `logoUrl`). `?country=AL|GB|IT|DE|GR` picks the country, `?country=all` lists every country, and without it the member's own country from sign-up is used (every country if they have none); `country` in the response is the filter that was applied (`null` = all), so show it as the selected value of a country picker. `POST /community/join` makes them a client of that gym with the details they signed up with (`201 { gymId, gymName }`, `409` if they already belong to a gym, `404` for an unknown or inactive gym). Every other endpoint answers `403` until they join; after joining, read `/me` again. A gym admin who adds a client with the email of a community member links that person to the gym instead of answering `409`. The mobile app shows only the gym list for such a member.

- A gym owner applies with `POST /signup-requests` (no session): owner name, email, phone, password, gym name, country, city, address, number of locations, optional notes. No account exists yet; the password is stored hashed. The response is `201 { data: { received: true } }`. A pending request or an account with the same email returns `409`. A rejected owner can apply again.
- The platform owner lists requests (`GET /signup-requests`, newest first, each with `status` `pending`, `approved` or `rejected`, `reviewNote`, `reviewedAt` and, once approved, the new `gymId`; never the password). `POST /signup-requests/:id/approve` creates the gym (country timezone, default timetable and one `Main` location, contact email and phone from the request) and a `gym_admin` account with the email and password the owner chose, in one transaction. `POST /signup-requests/:id/reject` takes `{ note }` (optional text, up to 500 characters). A request can only be reviewed once (`409` afterwards). Nobody is emailed; the owner just signs in after approval.
- Rate limits per client IP, answered with `429 { message, code: "RATE_LIMITED" }` and standard `RateLimit-*` headers: `POST /api/auth/sign-in/*` allows 10 wrong attempts per 15 minutes (a successful sign-in does not count) and `POST /signup-requests` allows 5 per hour. Show the message and let the user retry later.
